# Translations (i18n)

How user-facing UI strings are translated, and what a contributor does when
adding or changing one. The shorthand is the owner's request:

> I'd like to have some i18n, as I'd like to have pybabel or something, for all
> user-facing UI strings. I propose a `tr()` shorthand for strings needed to
> translate. — owner, 2026-09-15

## The shape: stdlib `gettext` at runtime, Babel at build time

- **Runtime is the standard library.** `clear_record.core.i18n` wraps
  `gettext`; `core` keeps its no-third-party rule (the layering guard,
  [ADR-0012](adr/0012-single-distribution.md)) and no runtime dependency is
  added at all.
- **Message IDs are the English source strings.** English needs no catalog, an
  untranslated string still renders correctly, and every existing test's exact
  English string keeps passing — adopting i18n is incremental.
- **Babel (`pybabel`) is a build-time tool only.** It lives in the `i18n`
  dependency group (root `pyproject.toml`) and is never imported at runtime.
- **The compiled catalog is committed.** `messages.mo` sits beside
  `messages.po` and `uv_build` ships both in the wheel, so a `pip install`
  carries the translation with no build step on the user's machine. This is the
  same source+tool-in-dev / compiled-output-committed / freshness-guard shape as
  the console's front-end assets ([docs/frontend-assets.md](frontend-assets.md),
  [ADR-0023](adr/0023-frontend-toolchain.md)).

```text
packages/clear-record/src/clear_record/locales/<lang>/LC_MESSAGES/
  messages.po   # translator-editable source (committed)
  messages.mo   # compiled, committed; what gettext reads at runtime
```

## The shorthand

`tr` and `trn` are the one lookup point — a Python import **and** a Jinja global,
so a template and a module cannot diverge:

```python
from clear_record.core.i18n import tr, trn

tr("Add project")
tr("Deleted {name}", name="Falcon")
trn("{count} file verified", "{count} files verified", n, count=n)
```

```jinja
<h2>{{ tr("Projects") }}</h2>
```

```python
from clear_record.core.i18n import deferred

# A string looked up *later* than module import (e.g. Click help, assembled
# after `--lang` is parsed): `deferred` marks it for extraction without
# translating now; `tr` looks it up at build time.
_DESCRIPTION = deferred("clear-record: from many recordings to one clear record.")
```

Placeholders are named `{name}` (not `%(name)s`). `trn`'s count argument is
positional-only, so a placeholder may also be named `n`.

### Making Babel see `tr` / `trn`

Babel does not know those names by default — that is the step that makes the
shorthand actually extract. `scripts/i18n.py` (and therefore the `just`
recipes) passes them explicitly:

```sh
pybabel extract -F packages/clear-record/babel.cfg \
    --keyword tr --keyword trn:1,2 --keyword deferred -o messages.pot \
    packages/clear-record/src/clear_record
```

`babel.cfg` maps the file patterns (`[python: **.py]`, `[jinja2: **.html]`); the
`jinja2` extractor comes from Jinja2 itself, which is why `jinja2` is in the
`i18n` group alongside Babel. `trn:1,2` names the first two arguments as the
singular/plural pair.

## Recipes

```sh
just i18n-extract    # re-extract source strings, merge into each messages.po
just i18n-compile    # compile each messages.po -> messages.mo
just i18n-check      # freshness guard: re-extract + re-compile, fail on drift
```

All three go through the `i18n` dependency group, so **`just verify` never needs
Babel** — a contributor who never touches a translation is not blocked.

`just i18n-check` is the guard and lives in its **own CI job** (`verify.yml` →
`i18n`), like `web-assets-check`. It compares the catalogs' *contents* (message
IDs, obsolete entries, and the compiled `.mo` bytes) rather than running `git
status`: Babel stamps a `POT-Creation-Date` header on every extraction, so a
byte-for-byte rebuild is never clean.

## Adding a string

1. Wrap the user-facing text in `tr("…")` (or `trn(...)` for a plural).
2. Run `just i18n-extract` — the string appears untranslated in each
   `messages.po`.
3. Run `just i18n-compile`.
4. Commit the source **and** the regenerated `messages.po` + `messages.mo`.

Do **not** edit a `.mo` by hand.

## Adding a locale

```sh
# from the repo root, with Babel available:
uv run --group i18n pybabel extract -F packages/clear-record/babel.cfg \
    --keyword tr --keyword trn:1,2 --keyword deferred \
    -o /tmp/messages.pot packages/clear-record/src/clear_record
uv run --group i18n pybabel init -i /tmp/messages.pot \
    -d packages/clear-record/src/clear_record/locales -l <lang>
just i18n-compile
```

Then translate the `.po` and commit it with the compiled `.mo`.

## What is never translated (a rule, not a preference)

- **JSONL log records** — a translated log line would break parsing.
- **The JSON API** — status values are machine-read.
- **Export artifacts** (Markdown / SRT / VTT / JSON) — the record is the user's
  data, in the language they spoke.
- **The diagnostics bundle** — redacted plain text for triage.

`tests/test_i18n_boundaries.py` installs a transforming pseudo-catalog and
asserts each of these stays English, so the boundary is enforced, not assumed.

## Locale selection

Precedence, highest first:

1. `--lang <tag>` (the CLI's global flag)
2. `CR_LANG`
3. `LC_ALL`
4. `LANG`
5. English

A locale with no compiled catalog falls back to English, so the list can name a
tag that does not ship yet. `clear-record --lang de --help` prints German help;
`clear-record web` renders German templates when `CR_LANG=de` or `LANG` names
`de`.

**Deferred** (stated rather than silently absent): the config-file layer (the
locale key would live in the service layer's config, which `core` may not read),
and the web console's `Accept-Language`/cookie negotiation. Both can be added
later behind the same `install`/`resolve_locale` seam.

## The catalogs that ship

- **`de`** — an initial, machine-assisted translation pending native review.
  Strings are translated across the console templates and the CLI help/errors;
  any untranslated ID falls back to English.

Deferred translation coverage: the pipeline-stage help strings and the
`diagnose`/`mcp`/`tray` subcommand help (they live in `core`/`service`/`mcp`/
`tray`, outside this slice's surface), and the per-option `--help` text of the
built-in commands (Click snapshots it when the decorators are built at import,
before `--lang` is parsed).

## Front-end interaction

The locale files live under `clear_record/locales/`, which Tailwind's `@source`
scan (`packages/clear-record/frontend/src/app.css`) does not cover and
`just web-assets-check` does not watch (`git status` is scoped to
`web/static/`). No exclusion is needed: translated text is data, not markup, and
no locale file is a front-end build input.
