# Translations (i18n)

How user-facing UI strings are translated, and what a contributor does when
adding or changing one. The shorthand is the owner's request:

> I'd like to have some i18n, as I'd like to have pybabel or something, for all
> user-facing UI strings. I propose a `tr()` shorthand for strings needed to
> translate. — owner, 2026-09-15

## The shape: stdlib `gettext` at runtime, Babel at build time

- **Runtime is the standard library.** `clear_record.core.i18n` wraps
  `gettext`; `core` keeps its no-third-party rule (the layering guard,
  [ADR-0012](adr/0012-single-distribution.md)) and no runtime dependency is
  added at all.
- **Message IDs are the English source strings.** English needs no catalog, an
  untranslated string still renders correctly, and every existing test's exact
  English string keeps passing — adopting i18n is incremental.
- **Babel (`pybabel`) is a build-time tool only.** It lives in the `i18n`
  dependency group (root `pyproject.toml`) and is never imported at runtime.
- **The compiled catalog is committed.** `messages.mo` sits beside
  `messages.po` and `uv_build` ships both in the wheel, so a `pip install`
  carries the translation with no build step on the user's machine. This is the
  same source+tool-in-dev / compiled-output-committed / freshness-guard shape as
  the console's front-end assets ([docs/frontend-assets.md](frontend-assets.md),
  [ADR-0023](adr/0023-frontend-toolchain.md)).

```text
packages/clear-record/src/clear_record/locales/<lang>/LC_MESSAGES/
  messages.po   # translator-editable source (committed)
  messages.mo   # compiled, committed; what gettext reads at runtime
```

## The shorthand

`tr` and `trn` are the one lookup point — a Python import **and** a Jinja global,
so a template and a module cannot diverge:

```python
from clear_record.core.i18n import tr, trn

tr("Add project")
tr("Deleted {name}", name="Falcon")
trn("{count} file verified", "{count} files verified", n, count=n)
```

```jinja
<h2>{{ tr("Projects") }}</h2>
```

```python
from clear_record.core.i18n import deferred

# A string looked up *later* than module import (e.g. Click help, assembled
# after `--lang` is parsed): `deferred` marks it for extraction without
# translating now; `tr` resolves it at call time.
_DESCRIPTION = deferred("clear-record: from many recordings to one clear record.")
```

Placeholders are named `{name}` (not `%(name)s`). `trn`'s count argument is
positional-only, so a placeholder may also be named `n`.

### Making Babel see `tr` / `trn`

Babel does not know those names by default — that is the step that makes the
shorthand actually extract. `scripts/i18n.py` (and therefore the `just`
recipes) passes them explicitly:

```sh
pybabel extract -F packages/clear-record/babel.cfg \
    --keyword tr --keyword trn:1,2 --keyword deferred -o messages.pot \
    packages/clear-record/src/clear_record
```

`babel.cfg` maps the file patterns (`[python: **.py]`, `[jinja2: **.html]`); the
`jinja2` extractor comes from Jinja2 itself, which is why `jinja2` is in the
`i18n` group alongside Babel. `trn:1,2` names the first two arguments as the
singular/plural pair.

## Recipes

```sh
just i18n-extract    # re-extract source strings, merge into each messages.po
just i18n-compile    # compile each messages.po -> messages.mo
just i18n-check      # freshness guard: re-extract + re-compile, fail on drift
```

All three go through the `i18n` dependency group, so **`just verify` never needs
Babel** — a contributor who never touches a translation is not blocked.

`just i18n-check` is the guard and lives in its **own CI job** (`verify.yml` →
`i18n`), like `web-assets-check`. It compares the catalogs' *contents* (message
IDs, obsolete entries, and the compiled `.mo` bytes) rather than running `git
status`: Babel stamps a `POT-Creation-Date` header on every extraction, so a
byte-for-byte rebuild is never clean.

## Adding a string

1. Wrap the user-facing text in `tr("…")` (or `trn(...)` for a plural).
2. Run `just i18n-extract` — the string appears untranslated in each
   `messages.po`.
3. Run `just i18n-compile`.
4. Commit the source **and** the regenerated `messages.po` + `messages.mo`.

Do **not** edit a `.mo` by hand.

## Adding a locale

```sh
# from the repo root, with Babel available:
uv run --group i18n pybabel extract -F packages/clear-record/babel.cfg \
    --keyword tr --keyword trn:1,2 --keyword deferred \
    -o /tmp/messages.pot packages/clear-record/src/clear_record
uv run --group i18n pybabel init -i /tmp/messages.pot \
    -d packages/clear-record/src/clear_record/locales -l <lang>
just i18n-compile
```

Then translate the `.po` and commit it with the compiled `.mo`.

## What is never translated (a rule, not a preference)

- **JSONL log records** — a translated log line would break parsing.
- **The JSON API** — status values are machine-read.
- **The MCP tool surface** — a tool's answer is data an agent reads, exactly as
  the JSON API's is. A refusal that reaches the model as a ``ToolError`` carries
  the service's own text: the run-options reader's sentence and detail (below),
  or a message ID left unrendered.
- **Export artifacts** (Markdown / SRT / VTT / JSON) — the record is the user's
  data, in the language they spoke.
- **The diagnostics bundle** — redacted plain text for triage.
- **A refused registry row's *detail***. A stored run-options row this build
  cannot read (`MalformedRunOptions`, `service/run_options.py`) is reported in two
  halves. The *frame* — which run, and that its stored options cannot be read — is
  a message ID, so the console's 409 page renders it in the reader's locale
  (`MalformedRunOptions.render`). The *detail* appended to it is the fields that
  failed in pydantic's own words (`jobs: Input should be a valid integer`), which
  is machine-facing and has no catalog entry by design: a script reads the same
  text through the JSON API's `detail`, and the run's own `error` column keeps it
  beside the row's text exactly as it stood (the lead-in above that text is a
  message ID, translated where the row is written).
- **A run's ``error`` column, in the three sorts of text that reach it.** The
  column is served verbatim by the JSON API and the MCP tool, so nothing in it is
  looked up by the surface that reads it: those two surfaces carry the stored text
  as it stands. Two frames are rendered where they are written (2 below), the only
  exception. What reaches it is one of:
  1. a **message ID** — the restart reconciliation's reason
     (``lifecycle.RESTART_REASON``) — which the console renders where it shows
     the column (``web/templates/_run.html``, ``_activity_run.html``);
  2. a **frame rendered where it is written**, in two cases that cannot be
     otherwise: revision ``0009``'s reconciliation reason, whose ``{run_id}`` only
     that revision's own statement can fill (``RECONCILED_REASON``), and the
     refused row's lead-in, which is a *prefix* of the row's own text; and
  3. the **detail** and any free text — a pipeline failure's own message — passed
     through exactly as it stood.
  The frames in (2) carry the locale of the process that wrote the row — the
  one that migrated the registry, or the one that quarantined the row — on every
  surface, which makes them the only machine-read values in this tree that are
  not locale-independent. That is a decision rather than an oversight: the
  alternative is an ID no surface can fill.

`tests/test_i18n_boundaries.py` installs a transforming pseudo-catalog and
asserts each of these stays English, so the boundary is enforced, not assumed.

## Locale selection

**The CLI** uses the chain in `clear_record.core.i18n.resolve_locale`:

1. `--lang <tag>` (the CLI's global flag)
2. `CR_LANG`
3. `LC_ALL`
4. `LANG`
5. English

**The web console** adds the two request-borne layers on top. Per request
(`clear_record.web.app.resolve_web_locale`), highest first:

1. the `cr_lang` **cookie** (the switcher's explicit choice)
2. the request's **`Accept-Language`** header (`zh-CN`/`zh` both match `zh_CN`)
3. `CR_LANG`
4. `LC_ALL` / `LANG`
5. English

A locale with no compiled catalog falls back to English, so the list can name a
tag that does not ship yet; a stale cookie or an unsupported browser preference
is skipped rather than guessed at, and the next layer decides. The web's
`--lang` is deliberately **not** in the chain — the console has its own
switcher, and the request wins. `clear-record --lang zh_CN --help` prints
Chinese help; `clear-record web` serves the locale the browser asks for.

**The cookie is the only new state.** It holds a language tag and nothing else
(no session, no identity), is `HttpOnly`/`SameSite=Lax`, and is set by the
switcher's own form POST.

The **config-file layer** remains deferred: the locale key would live in the
service layer's config, which `core` may not read. It can be added later behind
the same `install`/`resolve_locale` seam.

## The language switcher

The console header carries a two-option switcher beside its other controls
(`web/templates/base.html`, styled by `.lang-switch` in the compiled
stylesheet). Each option is shown as its **endonym** — `English` / `简体中文` —
on purpose: a picker that translated the language names would stop being
legible to the people who read them, so the names are literal, not `tr(…)`
message IDs. The current choice is filled in and marked `aria-current`.

It is a plain `<form method="post" action="/ui/language">` and a page redirect;
there is no client-side i18n framework. The endpoint stores the choice in the
`cr_lang` cookie (an unknown value stores nothing) and redirects to `/`.

## The catalogs that ship

- **`zh_CN`** — Simplified Chinese, prepared by the implementing agent and
  **awaiting native review**. The web console's user-facing text, user-facing
  CLI errors/usage errors and the tailscale status lines are translated; an
  untranslated ID falls back to English. See the catalog header for the exact
  coverage, and treat the copy as a draft until a native speaker signs off.

Deferred translation coverage: the `diagnose`/`mcp`/`tray` subcommand help
(they live in `core`/`service`/`mcp`/`tray`, outside this surface), and the
**per-option `--help`** text of the built-in commands — left English on purpose
("the line is the interface, not the terminal"): Click snapshots it when the
decorators are built at import, before `--lang` is parsed.

## Front-end interaction

The locale files live under `clear_record/locales/`, which Tailwind's `@source`
scan (`packages/clear-record/frontend/src/app.css`) does not cover and
`just web-assets-check` does not watch (its git query is the index — `git diff
--name-only`, plus untracked, unignored files — scoped to `web/static/`). No
exclusion is needed: translated text is data, not markup, and no locale file is a
front-end build input.
